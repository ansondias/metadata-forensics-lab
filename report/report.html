Digital Forensics · Experiment 07

Metadata Manipulation Beyond the Image

Extending the ExifTool EXIF/GPS exercise to three other containers — a Microsoft Word document, a PDF, and an audio file — to read, spoof, and hide data, then recover what a naïve wipe leaves behind.

Tool ExifTool 13.55 Host macOS (darwin 25.6) Specimens .docx · .pdf · .mp3 Date 2026-08-25

1 · Aim

Objective

The image lab showed that photographs carry invisible data — GPS coordinates, camera make/model, editing software, timestamps — that ExifTool can both read and rewrite. Documents, PDFs, and audio carry the same class of metadata in different containers. The aim here is to prove that the same read → spoof → hide → verify workflow transfers to those formats, to note where the tool's write support stops, and to show how an analyst detects the tampering.

2 · Theory

One idea, four containers

“Metadata” is data about the file that rides alongside the visible content. Each format stores it in its own envelope, but the exposure is identical — authorship, timestamps, tools, and free-text fields an attacker can abuse to hide a payload:

FormatWhere metadata livesHidden-text field
JPEGEXIF / IPTC / XMP segmentsComment, UserComment
DOCXdocProps/core.xml inside a ZIPdc:description, Keywords
PDF/Info dict + XMP streamSubject, Keywords
MP3ID3v2 frames prepended to audioCOMM (comment) frame

Baseline (image lab, for reference)

The prior exercise wrote a fake location and camera into a photo: exiftool -overwrite_original -GPSLatitude=33.9249 -GPSLatitudeRef=N -GPSLongitude=18.4242 -GPSLongitudeRef=E -Make=Apple -Model="iPhone 13" group.jpg — moving the pin from Mumbai to Cape Town and re-badging the camera. Below, the equivalent moves on the other three formats.

3 · Experiment A

AMicrosoft Word document

report.docxAuthor: Alice Fieldworker · Company: ACME Survey Group

A.1 — Read all metadata

ExifTool opens the ZIP and maps docProps straight into readable tags — the analog of exiftool photo.jpg.

exiftool report.docx

A.2 — Attempt to write with ExifTool

write attempt
$ exiftool -Creator="Bob Attacker" report.docx

    1 files weren't updated due to errors

Finding A-1

ExifTool reads OOXML but will not write it — the metadata is inside a ZIP it won't repackage. So we manipulate the XML part directly, which is trivially easy.

A.3 — Manipulate the container directly & verify

Unzip, edit docProps/core.xml (spoof the author, back-date both timestamps, inject a hidden note into dc:description), re-zip. ExifTool then confirms the forgery:

4 · Experiment B

BPDF document

report.pdfProducer: ACME PDF Engine 1.0

B.1 — Read all metadata

exiftool report.pdf
$ exiftool report.pdf
Title       : Quarterly Field Report
Author      : Alice Fieldworker
Creator     : ACME Survey Tool
Producer    : ACME PDF Engine 1.0
Create Date : 2026:03:14 09:12:00Z
Keywords    : survey, GPS, confidential

B.2 — Spoof metadata & inject a hidden comment

Unlike DOCX, PDF is in ExifTool's writable list — the same -overwrite_original syntax as the photo works verbatim:

spoof + inject
$ exiftool -overwrite_original \
     -Author="System Administrator" -Producer="Adobe Acrobat Pro" \
     -CreateDate="2020:01:01 00:00:00Z" -Keywords="cleaned" report_tampered.pdf
    1 image files updated
$ exiftool -overwrite_original -Subject="HIDDEN: exfil channel test 4E6F7465" report_tampered.pdf
    1 image files updated
$ exiftool -Author -Producer -CreateDate -Keywords -Subject report_tampered.pdf
Author      : System Administrator
Producer    : Adobe Acrobat Pro
Create Date : 2020:01:01 00:00:00Z
Keywords    : cleaned
Subject     : HIDDEN: exfil channel test 4E6F7465

B.3 — Recover the “deleted” metadata (counter-forensics)

ExifTool writes PDFs by incremental update: it appends a new revision and leaves the old one in place. The original author is still physically in the bytes — strings pulls it right back out.

forensic residue
$ strings report_tampered.pdf | grep -Ei "Alice|survey, GPS"
<< /Title (Quarterly Field Report) /Author (Alice Fieldworker)
   /Producer (ACME PDF Engine 1.0)
   /Keywords (survey, GPS, confidential) >>
$ ls -l report.pdf report_tampered.pdf
  892  report.pdf          # original
 4934  report_tampered.pdf # grew — both revisions retained

Finding B-1 · High value

An ExifTool “edit” on a PDF does not erase the prior value. The wiped author, keywords, and dates survive in the earlier revision, and the file grows — two tell-tales an analyst uses to prove tampering. Truly scrubbing a PDF requires a linearize/rewrite pass (e.g. qpdf --linearize), not a metadata edit.

5 · Experiment C

CAudio file (MP3 / ID3)

track.mp3Artist: Alice Fieldworker · ID3v2.3

C.1 — Read ID3 tags

exiftool track.mp3
$ exiftool -Artist -Title -Album -Year -Genre -Comment -AudioBitrate track.mp3
Artist        : Alice Fieldworker
Title         : Site Recording 12
Album         : Q1 Survey
Year          : 2026
Genre         : Speech
Comment       : Recorded on-site, mic 2
Audio Bitrate : 128 kbps

C.2 — Attempt to write with ExifTool

write attempt + capability check
$ exiftool -Artist="Bob Attacker" track.mp3
Error: Writing of MP3 files is not yet supported - track.mp3
$ exiftool -listwf | grep -Ei "mp3|m4a|wav|flac"
M4A   # MP4-family audio IS writable; MP3 / WAV / FLAC are not

Finding C-1

ExifTool reads ID3 fully but cannot write MP3, WAV, or FLAC — only the MP4 container family (M4A, MOV, MP4). To forge an MP3 tag you edit the ID3v2 frames directly (below); to do it with ExifTool you'd convert to .m4a first.

C.3 — Rewrite the ID3 frames directly & verify

Strip the old ID3v2 header, rebuild the frames with a spoofed artist/album, a back-dated year, and a hidden COMM comment, then re-read:

verify tampered mp3
$ # ID3v2.3 frames rewritten, audio stream untouched
$ exiftool -Artist -Album -Year -Comment track_tampered.mp3
Artist  : DJ Anonymous
Album   : Public Domain
Year    : 2015
Comment : (steg) HIDDEN: exfil channel test 4E6F7465

6 · Analysis

Comparative results

FormatExifTool readExifTool writeHidden-text vector usedForensic residue
JPEGyesyesCommentoverwrite in place
DOCXyesno → edit ZIPdc:descriptionclean re-zip
PDFyesyesSubject / Keywordsold revision retained ⚠
MP3yesno → edit ID3COMM frameframes replaced

All four formats leak authorship, timestamps, and tool fingerprints, and all four expose a free-text field an attacker can weaponize as a covert channel. The write path differs — ExifTool writes JPEG and PDF directly but hands off DOCX and MP3 to container-level editing — yet the metadata is equally forgeable in every case.

7 · Defensive takeaways

Detection & mitigation

  • Never trust metadata as evidence of authorship or time. Every field shown here was rewritten in seconds; timestamps and “Author” are attacker-controlled.
  • Hunt for residue. On PDFs, compare revision count and file growth (892 → 4934 bytes) and grep for prior values; on DOCX, inspect every part in the ZIP, not just what a viewer surfaces.
  • Look for impossible values. A 2020 create-date on a 2026 document, or Producer: Adobe Acrobat Pro on a file the logs say came from a survey tool, are contradiction signals.
  • Scrub before sharing. Strip metadata deliberately — exiftool -all= file.pdf, then linearize — rather than assuming an edit erased anything.
  • Inspect free-text fields for payloads. Comment / Subject / COMM fields are a known exfiltration and steganography channel; scan them, don't just display them.

8 · Result

Conclusion

The image-metadata workflow transferred cleanly to Word, PDF, and audio: in every container the metadata was read, spoofed, and used to hide a payload, and verified with ExifTool. The exercise also surfaced two limits worth remembering — ExifTool refuses to write ZIP-based DOCX and MP3 (forcing direct container edits), and its PDF writes leave the original values physically recoverable, which is exactly the seam a forensic analyst exploits to catch the forgery.
